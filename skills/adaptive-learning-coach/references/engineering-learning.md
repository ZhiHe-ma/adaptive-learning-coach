# 工程学习

读取条件：当前任务是代码理解、编程、测试、重构、代码审查或模块设计。只用下面命中的部分；工程规则不适用于语言或其他非工程学习。

## 代码理解六面体

围绕目标函数追踪六件事，按当前缺口取用，不每次重复完整清单：

| 面向 | 需要分清的证据 |
|---|---|
| 输入 | 来源、值、前置条件与边界输入 |
| 类型 | 数据是什么类型；对象、路径、文件内容和布尔值分别代表什么 |
| 处理 | 状态如何逐步变化，哪一步做关键判断 |
| 输出 | 返回了什么，返回值究竟承诺什么 |
| 调用关系 | 谁调用它，调用者如何使用返回结果 |
| 副作用／失败路径 | 改变了哪些外部状态，失败时保留、回滚或残留什么 |

引导教学时先让学习者预测，再用实际代码和受控实验核对；直接支持时由代理推进并交付结果。不要从函数名或返回 True 就推断磁盘已经写入；模拟模式、异常处理和调用者行为必须查看实际分支。

文件写入学习可观察：内存对象、临时文件、目标文件、返回值。成功、模拟运行、写入失败分别取证，尤其检查失败后原文件内容。临时文件清理、原子可见性和断电持久性是不同承诺，按当前实现与实验能支持的范围说明，不补造结果。

## 测试驱动开发

行为和公共接口明确，且目标适合通过测试表达时，使用测试驱动开发（Test-Driven Development）：先写一条能捕获目标失败的测试，观察红灯，再做最小实现使其变绿，最后在行为保持通过时整理。

每次推进一个纵向切片，即“一条外部行为＋验证它的测试＋最小实现”。预期来自目标契约、规格或独立算例，不能复制实现算法当作断言。

通过公共接口验证结果、错误行为和对外承诺；避免绑定私有函数、内部调用次数或实现结构。有项目测试约定时沿用。

接口仍在探索时，先用输入输出实例或短小实验明确行为；纯解释、轻量可逆修改等任务不强制 TDD。不要仅为通过本 Skill 流程而生成测试文件。

## 双轴代码审查

先确认审查对象及可用规格，再分别检查：

- **规格轴**：是否实现目标、返回值与边界行为是否正确、失败路径是否满足承诺。
- **标准轴**：是否清晰、符合项目约定、可维护、可测试，改动范围是否适当。

两轴不能互相替代。发现问题时附目标或约定、相关代码位置、具体影响及必要验证；缺少规格则标记缺口，不自造规格。审查请求本身不授权修复。不依赖 Issue 系统、其他审查 Skill 或并行代理流程。

## 模块设计

围绕当前改动说明责任、接口（Interface）、接缝（Seam）、状态、失败模式和测试表面。接口包括调用者必须知道的输入输出、顺序、约束与错误承诺；接缝是可替换行为或隔离依赖的位置。

追求深模块（Deep Module）：调用者学习较小接口，便能使用更多内部能力。例如调用者只需提交待保存数据并处理明确的成功／失败结果，模块内部承担序列化、临时写入与替换。以调用者负担和行为隔离判断深度，不用代码行数衡量。

优先在实际变化点设置接缝，让测试从接口观察效果；仅为假想扩展增加抽象会提高学习成本。设计讨论沿用项目术语，发生词义冲突时转状态参考处理。
