# 证据排错

读取条件：学习任务中出现错误、异常输出、流程失败或逻辑偏差；直接支持中的排错也使用本流程。

## 范围与因果链

用户只要求诊断时，停在根因、证据和未证实部分；用户已要求修复时，沿用当前授权完成最小修复与验证。教学不意味着要逐步索取同一授权。不能由“请解释错误”推断出修改授权。

1. **定义失败**：写清预期、实际和触发条件；保留与症状有关的输入、报错和环境差异。
2. **构造复现**：寻找最小但仍能出现同一症状的案例，先证明观察方式可以捕获这次失败。给出实际执行过的命令、步骤或观察结果；未执行就标记未执行。
3. **提出假设**：只保留有依据的可证伪原因。说明“如果原因是 X，则观察或改变 Y 后应出现 Z”；尚有竞争解释时不要提前宣布根因。
4. **区分假设**：选择最有信息量的一条日志、类型、状态或实验，一次改变一个变量。证据须能排除或支持具体假设，而不只是增加输出。
5. **确认后修复**：证据足够时定位因果链；已授权修复则做与根因对应的最小改动，不顺带重构无关部分。
6. **验证**：重跑原失败案例，再检查受影响的正常行为和关键边界。程序能启动或单次不报错不足以证明原问题消失。
7. **收束**：说明根因、改动与修复前后证据，列出尚未证明的部分。需要持久化时按状态参考处理。

## 无法稳定复现

优先在可控副本中缩小输入、固定必要条件，或有限次数重复触发并记录次数与失败率。不要为了提高复现率无限循环或向真实系统施压。

若仍无法复现，明确目前只有哪些静态证据、已尝试什么及缺少什么；提出一个最小取证动作，例如取得一次失败的脱敏日志。可以列出标为“待验证”的候选原因和区分方式，但不能把推测写成已定位、已修复或已验证。达到工具、时间或权限限制时保留该状态，不伪造运行证据。

## 风险与教学

涉及资金、权限或生产数据时，先核实执行目标、写入范围与可恢复性；优先使用实验副本、模拟输入或只读观察。在改变真实资源前满足项目所要求的授权和验证，不把教学示范变成真实交易、权限变更或生产写入。输出只保留必要的脱敏信号。

引导排错时让学习者先预测实验能区分什么，再观察证据；直接支持时由代理推进。代理查出的根因或完成的修复不能充当学习者独立排错的证据。
